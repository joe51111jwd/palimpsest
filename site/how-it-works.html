Mechanism

Put the validity interval in the primary key and supersession stops being a retrieval problem.

Nothing here is clever. A fact is stored under (entity, predicate), a new value closes the previous interval instead of coexisting with it, and both of the two time axes are kept separately rather than collapsed into one timestamp. What follows is what that buys, and what it costs.

01The ledger

Claims, not chunks.

A chunk store keeps the sentence. A claim store keeps the assertion the sentence made: an entity, a predicate, a value, and the interval over which that value held. The interval is not metadata bolted onto a record — it is part of the key, which is what lets a write close something instead of merely being added next to it.

The consequence is worth stating flatly, because it is the whole design: asking “what is true now?” is a key lookup. It is not a similarity search, it does not consult a model, and it cannot be wrong about which of two values is newer.

The ledger
(entity, predicate) ──► version chain

  (user, city): [ New York City | 2023-01-01 → 2023-04-11 ]
                [ Austin        | 2023-04-11 → open       ]  ← current

Nothing is ever deleted. The earlier versions stay in the chain, closed and dated, which is what makes as_of= time travel possible at all — and what makes the store auditable, since a value that changed leaves the record of what it changed from.

02Supersession

The failure a similarity search cannot fix from inside.

Take three utterances, months apart: “I just started at Initech”, “I work at Globex now”, “first week at Cyberdyne”. Ask where the user works. Every one of the three is an excellent semantic match, and nothing in the text of the stale ones marks them expired — being wrong does not make a sentence less similar to the question.

Attaching a timestamp to each chunk does not repair this. The stale chunk still scores well, still gets retrieved, and still arrives in the context window alongside the current one; the model is then asked to work out the ordering from three dated fragments, which is exactly the inference that should not be left to inference.

user · employer · version chain, valid time
Cyberdyne current 2024-01-08 → open
Globex superseded 2022-08-15 → 2024-01-08
Initech superseded 2021-03-02 → 2022-08-15
Illustrative example data. One current value; the rest dated and labelled. Resolving which is newer cost no model call, because the write that added Cyberdyne is the same operation that closed Globex.

The reader still sees the history when the history is what was asked for. A present-tense question drops the closed layers; a historical one is answered out of them. That is a filter on a chain the store already knows the shape of, not a re-ranking heuristic.

03Two axes

A change and a correction are not the same edit.

Bitemporal means two clocks, kept apart on purpose. Collapsing them into one updated_at column is the usual shortcut, and it destroys the distinction between “this used to be true” and “this was never true”.

Two time axes, kept separate
Valid time
When a fact was true in the world. Closed by a change — “I moved to Boston.” The past record stays true of the past.
Transaction time
When the store was told. Closed by a correction — “I was never at Globex, I misspoke.” It was never true at all.

Nothing is ever deleted, only closed. A correction closes the transaction-time interval of a record that should not have been believed; it does not rewrite history to pretend the record was never asserted.

user · employer · after a correction
Cyberdyne current 2024-01-08 → open
Globex corrected never true
Initech superseded 2021-03-02 → 2024-01-08
Illustrative example data. Struck through, not merely stepped back: a corrected value is excluded from every historical answer as well as the current one, which a superseded value is not.

An agent that cannot tell these apart gets both directions wrong. Treat a correction as a change and it will happily tell you the user worked at Globex until 2024. Treat a change as a correction and the user’s entire history disappears the first time they move house.

The API surface for both, with a worked example of the same three employers edited each way, is on the docs page.

04Open world

The hard part is not the ledger. It is making two names land on one key.

Supersession only fires if lives_in and city resolve to the same key. A closed-world system solves this by shipping a predicate whitelist and discarding everything outside it, which works until a user says something the author did not anticipate. This one is open-world: any predicate an extractor produces is admissible, so the canonicalizer has to earn the merge.

The obvious approach — embed the predicate name, merge above a cosine threshold — is not merely unreliable. Measured, the ordering is inverted:

Name-only cosine similarity between predicates
pair cosine relationship
lives_in ~ city 0.136 the same thing
favorite_food ~ least_favorite_food 0.842 opposite things
birth_year ~ birth_city 0.735 different things

Across the whole set, synonyms average 0.287 and traps average 0.495, and all six trap pairs land in the top 3 of their counterpart. Embedding the observed values rather than the names flips the ordering the right way round — synonyms 0.302, traps 0.101 — but the two distributions still overlap, so it is not thresholdable either. There is no cutoff that merges the synonyms without also merging favorite_food into least_favorite_food.

1 · Shortlist

Similarity is used only to narrow the field. The correct cluster is in the top-20 for 100% of predicates, which is all that is being asked of it — a recall instrument, never a decision.

2 · Adjudicate

An LLM decides which candidate in the shortlist, if any, is the same predicate. It sees a short list and answers a narrow question, which is the shape of task a model is actually reliable on.

3 · Veto

Deterministic guards — polarity, value-type, head-noun, role-suffix — hold a veto over the merge. They can exercise it; they can never override a refusal to merge.

Why the veto only points one way

A guard that could force a merge would be a whitelist again, wearing a different hat. The guards exist to make the model’s mistakes cheap: a wrongly blocked merge leaves two keys where one belonged, which shows up as a missed supersession. A wrongly forced merge silently fuses two different facts and corrupts both chains — a failure we have actually shipped and had to fix, and it is on the audit page.

Adjudication happens on write, and only for predicates the store has not seen before. Retrieval never calls a model. The measured contribution of the LLM adjudicator, and what the system scores with it switched off entirely, are in the ablations on the benchmarks page.

05Retrieval

Three tiers, fused, and the third one always runs.

recall() resolves the question to entities and predicates against the centroids the store actually learned — there is no hardcoded question vocabulary — then fills a token budget from three sources.

The three retrieval tiers, in the order they contribute
tier what it returns when it runs
interval The exact (entity, predicate) chain sliced at as_of — the value that was true, without the values that were superseded. When the question resolves to predicates.
graph Every fact about an entity named in the question, for multi-hop questions. When the interval tier has not filled k.
hybrid BM25 and dense retrieval over the raw utterances, fused by weighted reciprocal rank, lexical weighted above semantic. Always. Unconditionally.

Tier 3 running unconditionally is a correction of an earlier version that early-returned an empty context whenever its parser failed to fire. That scored well on a synthetic abstention metric and badly on real paraphrases. The rule is now flat: a non-empty store never returns an empty context.

None of this calls a model. recall() is pure Python and numpy, so the read path costs no tokens and no network round trip; the only LLM in the system extracts facts on write, and adjudicates an unfamiliar predicate. The tier-by-tier behaviour, with the returned object’s fields, is on the docs page.

06What it costs

What you give up.

Every one of these is a direct consequence of the design above, not an unfinished feature.

  • Extraction is a model call. Writes cost an LLM; reads do not. A store that is written to far more often than it is read from is the wrong shape for this engine.
  • What the extractor misses is not in the ledger. The claim layer can only supersede facts it was given. This is the failure mode behind the LoCoMo result below, and it is a real ceiling, not a tuning issue.
  • Narrative does not become claims. A long anecdote with no assertable fact in it lands in the hybrid tier and nowhere else — which is to say, on questions of that kind this is BM25 with extra steps.
  • Nothing is deleted. Storage grows monotonically with edits. That is the price of as_of=, and it is deliberate.

Where it loses

On LoCoMo, all 10 conversations, 468 questions: full_context wins at 0.549 on 23,604 tokens. bm25 at 0.417 and palimpsest at 0.408 are a statistical tie. Notably the other fact-layer baselines — mem0_style 0.237 and zep_style 0.278 — sit about 17 points below plain BM25 on the identical claims, which says the loss is a property of extracting claims from that corpus rather than of this engine in particular.

Read this with the number

On LongMemEval-S — all six categories, 470 questions, ~500 distractor sessions each — this engine is first at 0.536, [0.491, 0.581], against 0.472 for hybrid_rag, and the margin over second place clears an exact paired test (65 won / 35 lost, p = 0.0035). No earlier result here ever did, and the tables that predate this run said so. But the lead is category-shaped: on single-session recall the systems are level and bm25 beats both, on single-session preference we score the worst number on the board, and we lose LoCoMo.

Palimpsest

An open-world bitemporal claim-interval memory engine for AI agents. A palimpsest is a manuscript scraped and rewritten, where the earlier text stays legible underneath. So is this.
