Self-audit

In a memory system the dangerous bugs do not throw.

They return something plausible. Before publishing a number, an adversarial audit was run against this engine and its harness, hunting exactly that: failures that are silent, that look like legitimate output, and that a green test suite does not catch. It found nine defects. Six of the seven confirmed critical or major had survived a suite that was green at 305 tests.

The findings What fixing them cost us docs/AUDIT.md · tests/test_audit_regressions.py
01Method

Four lenses, each with a second agent whose job was to refute the first.

This project’s predecessor shipped three headline claims that did not survive review. So the audit came before the publication, not after it. Four independent lenses were run over the engine and the benchmark harness — bitemporal correctness, future leakage, canonicalization catastrophe, harness integrity — and every finding was then handed to a second agent tasked with knocking it down.

Every defect below was reproduced by running code, not by reading it. Several were measurably corrupting numbers this project was about to publish. All are fixed and pinned by regression tests in tests/test_audit_regressions.py.

9 defects found; seven confirmed critical or major
6 / 7 of the critical and major findings survived a green suite
305 tests passing at the time of the audit

The class of bug being hunted

Not a crash and not a wrong type. A memory store that answers is indistinguishable from a memory store that answers correctly, so the failure mode that matters is the one that returns a well-formed, confident, wrong block of context. Every finding on this page produced output that read as a legitimate answer.

02The archetype

The thing that motivated the exercise had already bitten twice.

Two defects in the claim cache are the reason the audit was scoped the way it was. Neither raised an error. Both silently changed what was being measured.

Cache defect — empty extractions silent

Empty extractions were cached.

A transient LLM timeout produced zero claims, and the empty list was written to disk, where every later run loaded it as a real result. 20 of 81 benchmark episodes had been silently zeroed — a quarter of a benchmark measuring a memory system, running with no memory at all.

Nothing errored, because “no facts extracted” is indistinguishable from “this conversation asserted no facts.”

Fixed: an extraction that failed is not a result and is not cached.
Cache defect — key ignored the episode favoured us

The claim cache ignored episode content.

LongMemEval ships the same 500 question ids across variants with different haystacks: oracle gives one question 24 messages, s gives that same id 413. Keyed on the id alone, the s run loaded the oracle variant’s claims — facts extracted from a haystack with every distractor already removed.

Not merely wrong. An unfair advantage to the system under test, on the exact axis — distractor robustness — this project makes its strongest claim about.

Fixed: the cache key covers the episode content, so a different haystack is a different key.
03The findings

Seven confirmed critical or major, in the order the audit reports them.

Read this as a log, not an apology. Each entry states what the defect was, what it did to output a reader would have believed, and what the fix changed.

Finding 01 critical ledger invariant

Cardinality was a property of a claim, never of a key.

The extractor labels each claim single or multi independently. Interval repair only ran for single claims, so one stray multi label disabled supersession for an entire attribute and left both values open. And because the neighbour search did not filter by cardinality, a multi atom sitting between two single atoms would itself get wrongly closed.

Keys holding two contradictory current values, measured on real extractions
corpus chains affected share
LongMemEval knowledge-update 33 of 78 episodes 42%
LoCoMo, single-valued chains 35 of 103 34%

A worked case, LongMemEval 9bbe84a2, gold answer level 100 — where the gold is the superseded value, the thing this engine claims to uniquely supply:

As extracted — with the bug 2 current values
user · goal · version chain, valid time
reach level 100 current since 06-16
reach level 150 current since 09-30
Both intervals open. The block asserts two contradictory facts as currently true and dates neither relative to the other.
After the fix 1 current value
user · goal · version chain, valid time
reach level 150 current since 09-30
reach level 100 superseded 06-16 → 09-30
The gold answer is the superseded layer. The bug converted a block that names it as the previous value into one asserting both as currently true.

Real extraction output for LongMemEval 9bbe84a2, redrawn in the site’s version-chain component. Dates are reproduced as the audit reports them.

Fix. Cardinality is decided per key by vote across its claims, and the chain is rebuilt when the vote flips, so the invariant holds by construction rather than by arrival order. After the fix: 137 single-valued chains on real LoCoMo data, 0 violations.

Why no test caught it

test_ledger.py tested single chains and multi chains in strict isolation. No test put both on one key, and no test asserted the invariant as a property over all chains — each hand-checked the one chain it built. There is now an assert_invariant() helper that walks every chain.

Fixed and pinned by a regression test.
Finding 02 critical inflated our own results

as_of was two different filters in one parameter.

Retriever.retrieve fed as_of to the fact tier as a valid-time bound (“what was true then”) while the excerpt tier used it as a transaction-time bound (“what had we been told by then”). The benchmark passes a question’s timestamp, which means the second.

So the fact tier answered from facts the store first heard months later, while the rendered header still said [Memory as of <cutoff>]. On LongMemEval this produced apparent wins where the gold answer reached this system and no baseline — for the excellent reason that no baseline can see the future either.

leak, reproduced
2133c1b5  asked_at=2023-10-15  gold='3 months'
   palimpsest         gold_in_context=True     <- leaked: atom valid_from 2023-10-15
   all six baselines  gold_in_context=False

Fix. known_at is a separate parameter; the two axes filter independently.

This is the defect that could see the future and inflate its own wins. Every affected benchmark artifact was discarded and re-run.
Finding 03 critical belief axis

Retroactive closures rewrote the past of the belief axis.

An atom stored one valid_to, mutated in place. So an interval closed today looked closed to a query about what was believed last week — the belief axis had no history of its own, which makes “bitemporal” decorative rather than true.

Fix. Atoms carry closed_tx, the transaction time at which valid_to was set. An as-of read ignores a closure the store had not yet learned.

Finding 04 critical public API

An unmatched retraction closed everything.

_retract_value looked the value up, and when the lookup missed it skipped the per-atom filter entirely — so “I don’t have a cat anymore”, with a value string the ledger had never stored, closed every open interval on the key.

Memory.correct() had the identical defect through the public API: correct("user", "city", "New York") against a stored "New York City" wiped the whole chain — and returned a success count.

Fix. A retraction or correction that matches nothing now affects nothing.

Finding 05 critical durable cache

A failed adjudication was cached as a permanent decision.

A failed LLM call and a genuine “these predicates are different” both surface as a falsy result, and the durable cache stored both identically. One run while the LLM was unreachable — or with PALIMPSEST_LLM_OFFLINE=1, which is how the tests run — permanently taught the store that lives_in and city are different predicates.

The store then served a superseded value labelled current, on the worked example the entire thesis rests on:

recall output
A) clean cache            B) cache poisoned by one offline run
  city: Austin              lives in: New York City   [current]   <- superseded
                            city: Austin              [current]

  supersessions: 1          supersessions: 0

Fix. Only a call that actually returned parseable JSON is cached. 762 poisoned declines were purged.

Finding 06 critical harness integrity

Accuracy and its confidence interval used different denominators.

The point estimate divided by judged rows; the Wilson interval divided by all rows. Whenever any question went unanswered, the interval was drawn around a different proportion than the number printed beside it.

In the first LongMemEval artifact an LLM outage left 20 of 72 questions unanswered, and every single reported accuracy fell outside its own reported CI:

first LongMemEval artifact, discarded
palimpsest  n=72  unjudged=20  acc=0.827  ci95=[0.482, 0.703]   acc in CI? False
bm25        n=72  unjudged=20  acc=0.615  ci95=[0.335, 0.559]   acc in CI? False

Worse than the arithmetic: excluding unanswered questions from the numerator’s denominator inflates accuracy, and nothing in the report said so.

Fix. One denominator, n_judged reported alongside n, and a run with more than 2% unanswered questions is flagged not reportable.

The 0.827 above is not a Palimpsest result. It is what the broken harness printed, and it is on this page instead of in a README.
Finding 07 major silent deletion

Same-instant claims created zero-length intervals.

Two values claimed true at the same instant produced an interval with valid_from == valid_to: unreachable by any as-of query, yet still suppressed from the excerpt tier as “stale”. A fact deleted in silence, in a store whose entire premise is that nothing is ever deleted.

Fix. A same-instant conflict is a conflict of belief, and resolves on the transaction axis.

04What it cost

Fixing the cardinality bug lowered our LoCoMo score, and the lower number is the one we publish.

The audit was not free and did not only produce reassurance. On the 3-conversation LoCoMo subset used during the audit, this engine scored 0.502 before the fix and 0.407 after it — a drop of 9.5 points, concentrated in the temporal category.

LoCoMo, 3-conversation subset, before and after the cardinality fix
measure before the fix after the fix
overall 0.502 0.407
temporal 0.629 0.514

The pre-fix score was higher because the bug created supersessions that should not have existed — a claim mislabelled multi skipped interval repair, and the resulting chaos happened to produce “earlier values” blocks that flattered the temporal category. Part of the apparent advantage was an artifact of a broken ledger.

A benchmark number that gets better when you fix a correctness bug is a number to be suspicious of. This one got worse, which is the expected direction, and it is the one on the benchmarks page.

Where it loses

On LoCoMo, all 10 conversations, 468 questions: full_context wins at 0.549 on 23,604 tokens. bm25 at 0.417 and palimpsest at 0.408 are a statistical tie. LoCoMo asks about details inside an utterance, which a fact ledger has nothing to say about.

05The numbers

Everything was re-run afterwards. Nothing measured before the fixes is reported.

Every benchmark result on this site was produced after these fixes. Numbers produced before them are not reported — including a LongMemEval knowledge-update figure that looked good and was measured on a ledger violating its own invariant, with a future leak, over 72% of the questions. It is gone, not softened.

The general lesson is the one the audit was designed around. In a memory system the dangerous bugs do not throw; they return something plausible. Six of the seven critical and major findings above survived a suite that was green at 305 tests, and each one produced output a reader would have believed.

Read this with the number

In both LongMemEval tables the confidence interval overlaps the runner-up, so the margin over second place is not statistically significant. The margin over BM25 and below is. And we lose LoCoMo.

Which is why you should not take this benchmark on faith either.

Across this field, self-reported memory scores do not reproduce when someone else measures them, and there is no public leaderboard anywhere to arbitrate. That is not a reason to trust the number on this site instead. It is a reason to trust the procedure: same process, same answering model, a judge separate from the answerer, the unmodified standard Mem0 judge prompt, the same token budget for every system, the identical extracted claims shared across every fact-based system — and a defect log published in full, including the two defects that were making our own results look better than they were.

The audit found nine. There is no claim here that nine is all of them.
