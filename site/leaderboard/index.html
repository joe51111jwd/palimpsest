Leaderboard

Until recently there was no public leaderboard for agent memory. Now there is one — and this is a different thing.

A row is admitted only if a stranger can re-run it: dataset file and its sha256, the denominator, the answering model, the judge model, the judge prompt, the averaging, the token budget, and the raw per-question records. Anything short of that is a claim, not a result — and that rule is applied to the maintainer’s own rows first.

00

The one that already exists

The Agent Memory Leaderboard launched on 29 July 2026 and is, as far as I can establish, the only live public ranking for agent memory. It is run by researchers across more than twenty institutions, it has real entries in both an academic and an industry division, and its benchmark suite includes longmemeval-s and locomo-refined. It settles the question of whether anything like this exists: it does, and it is better resourced than anything I can run.

It is also independent corroboration of the argument on the field page. Supermemory, which advertises 95 on LongMemEval, sits fourteenth of fifteen there. Mem0, which advertises 94.4, sits seventh. Those are not my measurements, and they say the same thing mine do.

So this page is not a competitor to it. AML evaluates through a closed box: you expose an Add and a Search endpoint, they run the datasets, the answering model and the judge, and you receive a score. That is the right design for making vendors comparable, and it is why I am submitting to it. What it cannot give you is the ability to re-run the evaluation yourself, because the harness and the per-question records are theirs.

That is the gap this page fills. Every row below can be recomputed from published JSON by someone who does not trust me, using a harness that is in the repository. The two are complementary: theirs is the independent scoreboard, this is the auditable one. Where our numbers eventually disagree, theirs is the one a stranger should believe, and I will publish the disagreement here.

01Disclosure

The person who runs this leaderboard has a system on it.

Palimpsest is mine. This leaderboard is mine. Palimpsest is first on two of the four boards below, second on a third, and third on the fourth. You should read every number here with that in mind, and this paragraph is at the top of the page rather than at the bottom because burying it would be the tell.

A leaderboard run by an entrant is only worth anything if the entrant’s row is the most exposed one on it. So the machinery below is arranged so that a favourable result cannot be produced quietly, and every rule that could have been softened for my own row was not.

What stops the maintainer from tilting this 6 controls
The judge is blind to the system
It receives the question, the gold answer and the generated answer, and nothing else — not the system’s name, not its context, not which run it came from (bench/judge.py, build_batch_judge_prompt).
One process, one configuration
Every system on a board is built and queried in the same run, on the same machine, from the same extracted claims, under the same token budget, answered by the same model and graded by the same judge. Nothing is cited from anyone’s table.
Every record is published
The raw per-question results are in the repository, wrong answers included. Any row on any board — mine first — can be recomputed from the JSON by someone who does not trust me.
Sampling is seeded
Where a subset was scored, it was drawn with random.Random(0) stratified across categories, so it is repeatable rather than lucky.
The losses are on the board
Palimpsest loses LoCoMo and loses LongMemEval oracle knowledge-update. Those boards are published at the same size, in the same place, with the same detail as the two it wins.
Nine defects published against my own engine
Including one where it could see the future and inflate its own results, and one whose fix lowered its LoCoMo score. Pre-fix artifacts were withdrawn rather than corrected. The audit log.
Rows whose system belongs to the leaderboard maintainer are marked maintainer in every table below, and the run by column names whoever executed the run.
02Why this exists

Every vendor publishes its own number, measured its own way.

There is no public leaderboard for agent memory anywhere. The benchmarks everyone quotes do not run one, so a reader comparing two published figures is comparing two different answering models, two judges, two denominators and sometimes two different datasets with the same name.

LongMemEval

No official leaderboard. The GitHub issue asking for one has gone unanswered since September 2025.

LongMemEval-V2

Has a leaderboard. It is empty.

LoCoMo

None at all — and no two published LoCoMo numbers measure the same thing.

The consequence is measurable. Self-reported scores in this field do not survive independent measurement: Mem0 self-reports 94.4 on LongMemEval and third parties measure 36–67; Supermemory claims 95 and is measured at 58.4; Zep claims 90.2 and is measured at 38–64. LightMem is the only system in the field whose self-report reproduces. The reproducibility problem, with sources →

03Admission

What a row must carry.

These are the fields that decide whether two numbers can sit in the same column. A submission missing any of them is rejected without further review — not because the number is doubted, but because nobody could ever falsify it. The full contract, including the review criteria and the removal policy, is in SUBMISSIONS.md.

Required fields, and what goes wrong when they are missing
field this leaderboard’s current rows why a row without it is rejected
dataset + version + sha256 longmemeval-cleaned, locomo10.json, hashes below “LongMemEval” names at least two different files. The widely-cited release was deprecated on 2025-09-19 and replaced by a cleaned one. Without a content hash, “version” is a word.
n, and the denominator rule 470 · 72 · 72 · 468, each explained Published figures called “LongMemEval” use n = 500, 470, 444, 367, 300, 282, 266, 150, 88, 50 and 15. A score without its denominator is not a score.
answering model haiku (an alias, not a pinned snapshot) The long-context baseline alone spans 14.0 to 82.40 across papers, driven by the model and its refusal behaviour rather than by any memory system.
judge model haiku, a separate call, blind to system identity Several published systems are graded by the model that answered. That is disclosable, not automatically disqualifying — silence about it is.
judge prompt mem0-standard-unmodified At least one published number uses a judge prompt with an added paragraph telling the judge to be generous on the one category it wins hardest.
averaging micro Micro versus macro moves a score by up to about 6 points on identical data. Almost nobody states which they used.
token budget 1,024 per question; full_context at 32,000 A system that wins on accuracy by spending 23× the tokens has not won the same contest. Any system running at a different budget is named.
what was scored generated_answer Measuring whether the retrieved context contains the gold string is retrieval hit-rate. It is a real metric, and it is not answer accuracy.
raw per-question results published, one record per question per system Every reported accuracy is recomputed from the records before a row is published. A row that does not re-aggregate is not published.
who ran it, and their interest leaderboard_maintainer An undisclosed conflict of interest removes the row. A disclosed one does not.

Two further gates, both machine-checked: a run in which more than 2% of questions went unanswered is not reportable, because excluding them from the denominator inflates accuracy silently; and baseline rows copied from another paper or README instead of run in the same process are not admitted at all.

04Standings

Four boards. One run card. Every row on it was executed in the same process.

The seven systems are the memory engine and six steelmanned baselines, all of them fed the identical extracted claims so that any gap between the fact-based systems is attributable to storage semantics rather than to somebody’s extractor prompt. Baselines are tuned to compete, not to lose: hybrid_rag is BM25 + dense with reciprocal-rank fusion, and it beats the engine on one of these boards.

05Submitting

Open a pull request with your results JSON and the command that produced it.

Any harness is acceptable. What is not optional is that the file carries the fields in §03, that its per-question records re-aggregate to the accuracy it claims, and that somebody else could run your command and get the same file. Reviews happen in the PR thread, in public, and rejected submissions keep their thread open so the rejection is auditable too.

submitting
# 1. fork, then run whatever harness you like
# 2. add ONE file:
leaderboard/submissions/<system>_<dataset>_<date>.json

# 3. open a PR titled:
leaderboard: <system> on <dataset>

# 4. state your relationship to the system in the body.
#    "independent" is a claim you are making publicly.
reproducing board 2 with this harness
./scripts/fetch_data.sh

python -m bench.run \
  --dataset longmemeval --variant s --all \
  --categories knowledge_update \
  --systems palimpsest,bm25,vector_rag,hybrid_rag,mem0_style,zep_style,full_context \
  --budget 1024 --model haiku \
  --out results/final/lme_s_knowledge_update.json

The commands behind the other three boards differ only in --variant, --categories, --dataset and --max-questions; all four are listed in SUBMISSIONS.md alongside the full field schema, the sha256 of all three dataset files, the ten hard rejection criteria, the conditions that are disclosed rather than rejected, and the policy for removing a row after publication.

SUBMISSIONS.md is a plain file next to this page, so it works offline. It also renders on GitHub, which is where the pull request goes.

A submission that contradicts a maintainer row is the most useful thing this page could receive. If your run shows the engine lower than it is published here, that PR gets merged and this page changes.

How these were checked, and how to get one corrected

Each line was verified against primary sources in August 2026 — arXiv full texts, vendor repositories, vendors’ own committed per-question results, and the dataset files themselves — and the working is in the field page. If a line here is wrong, or a vendor has since published the missing artifacts, open an issue and the row moves. The point of this section is the admission rule, not the list.

07Against us

What is wrong with the maintainer’s own rows.

A leaderboard whose operator is an entrant has to state its own weaknesses at least as plainly as anyone else’s. Every item below is a real limitation of the four boards in §04. None of these would get a submitter rejected — they are all in the “disclose it” column of SUBMISSIONS.md — because a rule the operator cannot pass is not a rule, it is a moat.

Known weaknesses of every row under run card R1 7 disclosures
The answering model is a moving alias
haiku is a CLI alias, not a pinned model snapshot. When the alias moves, these runs stop being bit-reproducible, and no re-run after that point is strictly comparable to this one. A pinned snapshot id would be better and is not what was used.
The judge runs on that same alias
The judge is a separate call that never sees which system produced an answer, and it uses the standard prompt unmodified — but it is the same model as the answerer. That is a weaker separation than a different-family judge, and this field has criticised exactly that arrangement in other systems.
LoCoMo is a sample, not the whole benchmark
Board 4 draws 60 questions per conversation with random.Random(0), stratified across categories — 600 in all, of which the 132 adversarial ones are reported separately, leaving 468 scored. The non-adversarial pool is 1,540 questions. It is seeded and repeatable; it is not the full set.
The oracle boards are upper bounds
Boards 1 and 3 use the oracle haystack, which has no distractors. That is an upper bound on retrieval, not a retrieval result. The distractor-laden board is Board 2, and it is the one this design should be judged on.
Denominators are 470 and 72, not 500 and 78
The 30 LongMemEval abstention variants are excluded from accuracy and reported separately. That is a defensible choice and it is still a choice, made by the person whose system is on the board.
The engine has known defects, nine of them found
Four adversarial audits against this engine and its own harness found nine, and six of seven confirmed defects had survived a suite passing at 305 tests. One of them produced a knowledge-update figure measured on a ledger violating its own invariant, with a future leak, on over 72% of the questions. Another’s fix lowered the LoCoMo score by 9.5 points on a three-conversation subset, because part of the apparent advantage had been spurious supersession. Every number above was re-run afterwards and the pre-fix artifacts were withdrawn rather than corrected. The log →
Margins that are not significant are marked as such
On Boards 1 and 2 the interval overlaps the runner-up, so first place is not a statistically significant win over second. The caveat saying so sits beside those tables, and it travels with either number wherever else it appears on this site.
If you can show any of these is worse than described, that is a bug report against this page and it will be treated as one.
08Status

One submitter is not a leaderboard yet.

Four boards, seven systems, one run card, one submitter. What exists so far is a standard and a worked example of applying it to oneself. It becomes a leaderboard when somebody else submits a row, and it becomes a useful one when somebody else’s row beats the maintainer’s.

Until then the honest description is: an open harness, published raw results, an admission rule written down before the results were, and a standing invitation to contradict them.
