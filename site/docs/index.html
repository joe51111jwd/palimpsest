Documentation

Install it, store five facts, and ask what was true last April.

The quickstart below runs offline with no LLM and no API key. After it, the six concepts you need before the API reference reads as anything other than a list of method names: claims and version chains, the two time axes, cardinality, canonicalization, the three retrieval tiers, and what this engine deliberately refuses to do.

01Install

Three dependencies, no GPU, no service to run.

Python 3.11 or newer. The runtime dependencies are numpy, model2vec and tiktoken — no torch, no CUDA, no ONNX runtime, nothing to stand up alongside your process. Storage is SQLite, and the schema is plain SQL that ports to Postgres.

shell
pip install palimpsest-memory
320 tests, CI green on Python 3.11–3.13
3 runtime dependencies, none of them torch
3.11 minimum Python version

What happens on the first Memory()

Canonicalization embeds a predicate string on every ingest, so the embedder sits on the hot write path. The default backend is the model2vec static model minishlab/potion-base-8M, which is a distilled lookup table — embedding is a matrix gather plus a mean, in microseconds, on a CPU. The first construction in a fresh environment fetches it.

If it cannot be fetched or found in the cache, the embedder falls back to a deterministic hashing embedder rather than raising, so the package always imports and tests run in a bare environment. That fallback is much weaker at resolving a question to a predicate, so it is worth checking which one you actually got:

python
from palimpsest import Memory

mem = Memory()
print(mem.embedder.backend)
# model2vec:minishlab/potion-base-8M   <- the real one
# hashing                                <- the offline fallback
02Quickstart

Sixty seconds, offline, deterministic.

An extractor normally turns raw messages into claims using an LLM. Here the claims are handed in directly, which is a first-class path — ingest(messages, claims=...) is the same path the benchmark harness uses so that extraction is paid for once, in one cached batch, instead of inside the ingest loop. It also means this example needs no API key and produces the same output every time.

python
from datetime import datetime

from palimpsest import Memory, Message
from palimpsest.types import Claim


def at(y, m, d):
    return datetime(y, m, d, 12, 0)


# msg_id, text, when, predicate, value, cardinality
TURNS = [
    ("m1", "I live in New York City.",       at(2023, 1, 1),  "city",        "New York City", "single"),
    ("m2", "I work at Globex.",              at(2023, 2, 3),  "employer",    "Globex",        "single"),
    ("m3", "I'm allergic to penicillin.",    at(2023, 3, 9),  "allergic_to", "penicillin",    "multi"),
    ("m4", "Just moved to Austin!",          at(2023, 4, 11), "lives_in",    "Austin",        "single"),
    ("m5", "My new employer is Pied Piper.", at(2023, 6, 2),  "employer",    "Pied Piper",    "single"),
]

messages, claims = [], []
for msg_id, text, when, predicate, value, card in TURNS:
    messages.append(Message(session_id="s1", speaker="user", text=text,
                            timestamp=when, msg_id=msg_id, role="user"))
    claims.append(Claim(entity="user", predicate=predicate, value=value,
                        cardinality=card, source_text=text, source_id=msg_id))

mem = Memory()
print(mem.ingest(messages, claims=claims))

print(mem.recall("Where do I live?").context)

for fact in mem.timeline("user", "city"):
    print(fact.as_line())
output

             retractions=0, noops=0, predicates_minted=3,
             predicates_aliased=4, latency_ms=3.29)

  - The user's city: Austin   [since 2023-04-11]

RELEVANT CONVERSATION EXCERPTS:
  [2023-02-03] user: I work at Globex.
  [2023-04-11] user: Just moved to Austin!
  [2023-06-02] user: My new employer is Pied Piper.
  [2023-03-09] user: I'm allergic to penicillin.

You — city: New York City  (was true 2023-01-01 to 2023-04-11, superseded)
You — city: Austin  (current, since 2023-04-11)

Three things in that output are the whole product. New York City is absent from the fact block — not ranked lower, absent, because its interval is closed. Five claims produced three canonical predicates from four surface forms — lives_in and city landed on one key, which is the only reason the move to Austin superseded New York instead of sitting beside it. And the closed interval is still there, visible in the timeline, which is what makes as_of= possible at all.

The excerpt block underneath is not a bug. The ledger answers attribute questions; the raw utterances stay indexed for everything else. See the three tiers.

03Claims

A claim is an assertion. An atom is an interval. A chain is the history.

A Claim is what an extractor emits: an open-world, grounded assertion with a raw predicate name — whatever the extractor found natural, be it lives_in, city or residence. Extractors are deliberately dumb about identity so they stay swappable; deciding what a name means is the ledger's job, not theirs.

Folding a claim into the ledger canonicalizes its entity and predicate into integer ids, and appends an Atom — one interval — to the chain for that (entity_id, predicate_id) key. Everything the engine claims about correctness reduces to one invariant on that chain:

For a given key with single cardinality, the valid-time intervals of its believed atoms are disjoint and ordered, and at most one is open.

Maintaining that on write is what makes “what is true now?” a head lookup instead of a similarity search over mutually contradictory chunks, and it is why contradiction resolution costs no LLM call.

user · employer · version chain, valid time
Cyberdyne current 2024-01-08 → open
Globex superseded 2022-08-15 → 2024-01-08
Initech superseded 2021-03-02 → 2022-08-15
Three writes, three atoms, one open interval. timeline("user", "employer") returns exactly these, oldest first.

Three write behaviours worth knowing before you are surprised by them

  • A repeat is a no-op. An identical value at or after the head does not append an atom; it nudges the head's confidence up and increments its access count. Mentioning your city forty times does not produce forty intervals.
  • Late claims about the past are spliced, not appended. “I moved to Austin last spring” is learned today and was true in April. The insert finds its slot in the chain and repairs both neighbours, so a late arrival about the past cannot corrupt the present.
  • Two values claimed true at the same instant are a conflict of belief, not a change over time. Closing valid time there would mint a zero-length interval that no as_of query can ever return, so the conflict is resolved on the transaction axis instead.

A Fact is the id-free public view of an atom, and it is what every read method hands back. Nothing is ever deleted from the ledger — only closed.

04Two axes

A change and a correction are not the same edit.

This is the part of the design that the word bitemporal has to earn. An earlier version of this engine collapsed the two axes into one, which meant a correction and a change were indistinguishable. They are not.

Two time axes, kept separate
Valid time
valid_from / valid_to — when the fact was true in the world. Closed by a change: “I live in Boston now.” The New York interval stays true of its own past.
Transaction time
tx_from / tx_to — when the store was told. Closed by a correction: “I was never at Globex, I misspoke.” It was never true at all, so valid time is left untouched and the record stops being believed.

There is a third stamp that is easy to miss: closed_tx, the transaction time at which valid_to was set — when the store learned that a value had ended, as distinct from when it ended in the world. Without it, a retroactive supersession rewrites the past of the belief axis, and a query about what you knew last week can see this week's closure.

Worked example: the same three employers, edited two ways

Start from the chain above — Initech, then Globex, then Cyberdyne — and run one correction against it.

python
# after ingesting Initech (2021-03-02), Globex (2022-08-15), Cyberdyne (2024-01-08)

for fact in mem.timeline("user", "employer"):
    print(fact.as_line())

# You — employer: Initech    (was true 2021-03-02 to 2022-08-15, superseded)
# You — employer: Globex     (was true 2022-08-15 to 2024-01-08, superseded)
# You — employer: Cyberdyne  (current, since 2024-01-08)

print(mem.correct("user", "employer", "Globex"))   # -> 1

for fact in mem.timeline("user", "employer"):
    print(fact.as_line())

# You — employer: Initech    (was true 2021-03-02 to 2024-01-08, superseded)
# You — employer: Cyberdyne  (current, since 2024-01-08)
A change valid time
user · employer · after three normal writes
Cyberdyne current 2024-01-08 → open
Globex superseded 2022-08-15 → 2024-01-08
Initech superseded 2021-03-02 → 2022-08-15
Every value was true, in order. Ask as_of=2023-01-01 and you get Globex, correctly, because it really was the answer then.
A correction transaction time
user · employer · after correct(…, "Globex")
Cyberdyne current 2024-01-08 → open
Globex corrected never true
Initech superseded 2021-03-02 → 2024-01-08
Globex stops being returned for any as_of, and its predecessor reopens to cover the gap — Initech now runs to 2024-01-08. The row is still in the database; it is simply no longer believed.

A correction that matches nothing corrects nothing

correct() matches the value case-insensitively and exactly. correct("user", "city", "New York") against a stored "New York City" returns 0 and changes nothing. An earlier version wiped the whole chain and reported success; that is defect log material, and it is why the return value is a count you should check.

05Cardinality

Cardinality belongs to the key, not to the claim.

single means a new value replaces the old one: city, employer, job title, marital status, age. multi means several coexist: hobbies, children, allergies, pets, skills, and any one-off event. Supersession only fires on single-valued keys — that is the entire difference.

Every Claim carries a cardinality label, but the ledger does not obey it claim by claim. It votes: whichever label the claims on a key have carried more often wins, and every atom on that key is governed by that one decision. When the vote flips, the chain is rebuilt so the invariant holds by construction rather than by the order claims happened to arrive in.

That indirection exists because an extractor labels each claim independently, and one stray multi used to disable supersession for a whole attribute: a stray claim never closed its predecessor, and both values stayed open. Measured on real extractions, 42% of LongMemEval knowledge-update episodes ended up holding two contradictory values as simultaneously current — on the exact category this engine exists to get right. The measurement is recorded in the comment on Ledger.apply in palimpsest/ledger.py.

python
claims = [
    Claim(entity="user", predicate="allergic_to", value="penicillin",
          cardinality="multi", source_text=..., source_id="c1"),
    Claim(entity="user", predicate="allergic_to", value="shellfish",
          cardinality="multi", source_text=..., source_id="c2"),
]
mem.ingest(messages, claims=claims)

for fact in mem.timeline("user", "allergic_to"):
    print(fact.as_line())

# You — allergic to: penicillin  (current, since 2023-01-04)
# You — allergic to: shellfish   (current, since 2023-01-09)
# both open — shellfish did not close penicillin

A negative-polarity claim is the other way a multi-valued interval ends. “I don't have a cat anymore” closes the interval without opening a successor, which is a different shape of edit from “I moved to Boston”. A retraction whose value the store never held retracts nothing — not everything, which is what an earlier version did.

06Canonicalization

The hard part is not the ledger. It is making two names land on one key.

If “I moved to Austin” mints lives_in and “my city is Austin” mints city, supersession never fires, both values stay open, and the whole thesis collapses into an ordinary fact list with extra steps. A closed predicate whitelist makes the problem disappear by making the system useless: it refuses to store anything it was not hardcoded for.

The obvious alternative — embed the predicate name, merge above a cosine threshold — is measurably backwards.

Name-only cosine similarity between predicates
pair cosine relationship
lives_in ~ city 0.136 the same thing
favorite_food ~ least_favorite_food 0.842 opposite things
birth_year ~ birth_city 0.735 different things

The ordering is inverted: synonyms average 0.287, traps 0.495, and all six trap pairs land in the top 3 of their counterpart. Embedding the observed values alongside the name flips the ordering (synonyms 0.302, traps 0.101) because synonymous predicates draw values from the same distribution — but it is still not thresholdable, since liking and hating a thing produce identical value distributions.

So similarity is used as a shortlist and never as a decision. The write path is:

1 — Alias hit

Exact match against every surface form seen before. O(1), and the common case once the vocabulary warms up: novel names become rare fast, so the rest amortizes toward zero.

2 — Shortlist

Top-k canonical predicates by embedding rank, no threshold. Measured on a 60-predicate vocabulary, the correct cluster is in the top-20 for 100% of predicates.

3 — Adjudicate

An optional callable — in practice one batched LLM call over the novel predicates in a chunk — picks a candidate or declines. A model is very good at picking from twenty candidates. Answers are cached by (raw, candidate-set).

4 — Veto, then mint

Deterministic guards can overrule a merge but can never force one: value-type, polarity, head-noun, role-suffix. They independently catch all six trap pairs. If nothing merges, the predicate is minted as new.

The seed synonyms, and why they are not a whitelist

Twenty seed groups ship in palimpsest.canon.SEED_SYNONYMS — the attributes that come up in almost every personal memory: city / lives_in / residence / hometown …, employer / company / works_at …, job_title / occupation / role …, and so on through partner, food preference, car, pet, phone, email, age, birthday, allergies, diet, project, goal, hobby, timezone, language and school.

They restrict nothing. A predicate outside every group is stored exactly as it would be without them. They exist because the common cases should work with no LLM configured at all — without them, a bare Memory() mints lives_in and city as separate keys (their cosine similarity is 0.136), supersession never fires, and the headline promise fails silently, which is the worst way for it to fail. Pass your own list to the Canonicalizer if the defaults are wrong for your domain.

To get adjudication on everything else, hand Memory an adjudicator. It is any callable matching (raw, candidates, value_type) -> str | None.

python
from palimpsest import Memory
from palimpsest.extract.adjudicator import LLMAdjudicator, StaticAdjudicator

# deterministic, zero LLM calls — for tests and offline runs
mem = Memory(adjudicator=StaticAdjudicator([{"pet", "animal_companion"}]))

# or a real model: any callable taking a prompt and returning parsed JSON
mem = Memory(adjudicator=LLMAdjudicator(client.complete_json))

One failure mode is worth knowing about because it is silent and durable: a failed LLM call and a genuine “these are different” both surface as a falsy result. Caching the first as if it were the second permanently teaches the store that lives_in and city are different predicates, and it then serves a superseded value labelled current. The adjudicator distinguishes the two and refuses to cache a failure.

Online canonicalization against a growing predicate vocabulary is not itself novel — DIAL-KG (arXiv 2603.20059, DASFAA 2026) does frequency-gated cluster promotion with LLM schema evaluation. What is contributed here is the interval-ledger consumer of it, and the measurement that value-profiled similarity is a shortlist-only signal.

07Retrieval

Three tiers, fused, and the third one always runs.

recall() first builds a plan from the question with no hardcoded predicate vocabulary: entities come from name mentions and first-person pronouns, and predicates are resolved by embedding the question against the canonical predicate centroids the store actually learned. A store that has never heard of city resolves “where do I live?” against whatever predicate it did learn.

The three retrieval tiers, in the order they contribute
tier what it returns when it runs
interval The exact (entity, predicate) chain sliced at as_of — the value that was true, and nothing that was superseded. When the question resolves to predicates.
graph Every fact about an entity named in the question, for multi-hop (“what does my sister do?” once “my sister” is bound to Maria). When the interval tier has not filled k.
hybrid BM25 and dense retrieval over the raw utterances, fused by weighted reciprocal rank, with the lexical side weighted above the semantic side. Always. Unconditionally.

Tier 3 being unconditional is a deliberate correction of an earlier version, whose retriever early-returned an empty context whenever its keyword parser failed to fire. That scored well on a synthetic abstention metric and catastrophically on real paraphrases. The rule now is flat: a non-empty store never returns an empty context.

The interval tier also feeds the hybrid tier something a vector store cannot express. Semantic search happily returns “I work at Globex” long after the user moved, because the sentence is still an excellent match for “where do I work?” — nothing about the text marks it expired. The chain knows exactly which utterances have been overtaken, so present-tense queries drop them. Historical questions explicitly want them, so the filter does not apply there.

python
r = mem.recall("Where do I work?")

print(r.n_tokens)               # 117
print(r.resolved_predicates)    # ['employer', 'city']
print(r.resolved_entities)      # ['user']
print(r.tier_counts)            # {'interval': 2, 'graph': 1, 'hybrid': 3}

for rf in r.facts:
    print(rf.tier, rf.score, rf.fact.value)

# interval 3.0 Pied Piper
# interval 3.0 Austin
# graph 1.5 penicillin

recall() is pure Python and numpy. It calls no model. The token_budget is a hard ceiling on context, defended after packing rather than merely estimated, and the fact block gets a fraction of it that depends on how confidently the question resolved to a predicate. On a historical question the superseded values are the answer, so they get the fact budget first — filling it with current values and letting the past block fall off the end would be the exact failure this engine exists to avoid, inverted.

08Limits

What this deliberately does not do.

It is not smaller than your transcript

The raw utterances stay indexed, because plenty of questions are not attribute lookups — “what did the charity race raise awareness for?”. The store is roughly transcript-sized plus a quantized index. The ledger earns its keep on correctness, not bytes. An earlier version of this project claimed a 181× storage win; that was an artifact of benchmarking an fp32 baseline against its own quantized index, and the claim is retired.

It needs an LLM to write, not to read

Facts have to be extracted from raw text by a model, and novel predicates are best adjudicated by one. Retrieval itself calls nothing: it is Python and numpy, CPU-only. Supply pre-extracted Claims and the write path needs no model either.

It is not a vector database

It uses one, as one tier of three. If your questions are about the content inside an utterance rather than the current value of an attribute, a fact ledger has nothing to add and you should expect it to tie with plain BM25 at best.

Where it loses

On LoCoMo, all 10 conversations, 468 questions: full_context wins at 0.549 on 23,604 tokens. bm25 at 0.417 and palimpsest at 0.408 are a statistical tie. LoCoMo asks about details inside an utterance, which a fact ledger has nothing to say about. All four tables →

Read this with the number

In both LongMemEval tables the confidence interval overlaps the runner-up, so the margin over second place is not statistically significant. The margin over BM25 and below is. And we lose LoCoMo.
