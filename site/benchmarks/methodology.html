Benchmarks · methodology

The harness is the deliverable. The score is just what came out of it.

Every system on the results page runs in one process, on one machine, with the same answering model, the same judge, the same unmodified judge prompt, the same token budget, and the identical extracted claims. Nothing is cited from a vendor’s table. This page is how that is enforced, how to run it yourself, and why almost no published number in this field can be placed beside another one.

01The harness

Six things are held constant, and they are the six that usually are not.

Each of these moves a score by more than most architectural choices do. Fixing them is what makes seven systems comparable to each other; printing them is what lets a reader decide whether the comparison is worth anything.

One process

Palimpsest and every baseline run in the same process on the same machine, on the same data, in the same run. No number in a results table was produced on a different day, a different machine or a different model than the rows beside it.

One answering model

claude-haiku turns context plus question into an answer, for every system. A memory system is measured by the answer a model gives from its context, not by whether the right passage was somewhere in the index.

A judge that is not the answerer

Grading is a separate call from answering. Several published systems are judged by the same model that produced the answer — including the highest verified score in the field — which measures self-agreement as much as correctness.

The standard judge prompt, unmodified

The Mem0 formulation (arXiv 2504.19413), used as published. Not reworded, not extended, and with no per-category instruction added. A judge asked to “be generous” on one category is not the same instrument as one that is not.

One token budget

1,024 context tokens for every retrieval system, and mean tokens used are published beside every accuracy. A system that wins by putting 2,000 more tokens in the prompt has not won. full_context is the one exception and is labelled as an upper-bound reference, not a budget-matched competitor.

Identical extracted claims

One shared LLM extraction pass per episode, cached on disk. Palimpsest, the Mem0-style flat fact layer and the Zep-style temporal graph all receive the same claims, so any gap between those three is attributable to storage semantics rather than to somebody’s extractor prompt.

The protocol, in order

  1. Extract claims once per episode, cached on disk, shared by every fact system.
  2. Each system ingests the same messages and the same claims.
  3. Each system returns a context for each question under the same token budget.
  4. One answering model turns context plus question into an answer.
  5. One judge model grades the answer against gold, using the unmodified Mem0 prompt.

Accuracy is micro-averaged — question-weighted, not category-weighted — and its confidence interval is computed on the same denominator as the accuracy it sits beside. That last sentence exists because an earlier version of this harness did not do it, and the audit caught it.

What is not controlled

The extractor is an LLM, so the claim set for an episode is not bit-reproducible across providers or model versions. It is cached per episode and shared, which removes it as a source of difference between systems in one run, but it does not make the absolute numbers portable to a different extractor. Latency is measured as retrieval time only, not end-to-end, and was measured on one laptop.

02Baselines

The baselines are steelmanned on purpose.

MemDelta (arXiv 2606.29914) rebuilt the baselines Mem0 compared against and found the advantage was almost entirely a baseline-quality artifact: an advertised +11pp over RAG became −1.2pp once the RAG baseline was given a decent embedding model, with nothing about the memory system changed. A memory system measured against a weak RAG baseline has measured the baseline.

  • hybrid_rag is BM25 + dense with reciprocal rank fusion — the strongest simple baseline, and it frequently beats both of its components. It is the runner-up in both LongMemEval tables and the reason the caveat on those tables exists.
  • vector_rag gets a binary-quantized index and a sane top-k, rather than a configuration chosen to lose.
  • bm25 is plain lexical retrieval, and it wins LoCoMo among budget-matched systems. It is kept in every table for exactly that reason.
  • full_context runs at 32,000 tokens and is reported as the upper-bound reference it is, with its token cost printed next to everyone else’s. Comparing it at 1,024 tokens would measure the truncation rather than the method — at that budget a 419-message episode keeps only its last ~15 messages and scores near zero. It wins LoCoMo outright.
  • mem0_style and zep_style are flat-fact-layer and temporal-graph re-implementations in this harness. They are not the vendors’ products and are never labelled as such — they are the storage semantics, fed the identical claims, so the comparison isolates the semantics.

The predecessor of this project failed its own audit for choosing baselines that would lose, and the fix is documented rather than hidden.

03Exclusions

What is excluded, and why — before the score, not in a footnote.

Dropping questions is the cheapest way to move a benchmark number, so every exclusion here is named, counted and justified.

LoCoMo category 5, adversarial, 446 questions

Excluded from the headline and reported separately. Its adversarial_answer field is not an abstention target: 74.7% of those questions name the speaker who did not utter the evidence, and the field holds the answer you give if you fall for the misattribution. Scoring it by string-matching that field rewards the hallucination the category exists to detect. Instead the harness reports misattribution resistance: the fraction of category-5 questions where the model did not assert the adversarial answer.

Excluding category 5 also matches what Mem0, Memobase and Backboard do, so the headline stays comparable to published numbers — rather than calling 1,540 questions “the full benchmark”.

LongMemEval abstention variants, 6 of 78 knowledge-update questions

The knowledge-update category has 78 questions, of which 72 are scored; six are abstention variants and are reported separately. Every knowledge-update table on the results page says n = 72 in its caption, and the judged count is printed in its own column so a reader can see that nothing was silently dropped between the two.

TODO — 1,540 non-adversarial questions, 468 judged

Excluding category 5 leaves 1,540 questions, but the headline LoCoMo run on the results page judges 468. The selection rule that produces that number is not written down anywhere on this site and is not being guessed at here. It has to be stated beside the table, since an undocumented denominator is the exact failure this page accuses others of.

Category labels

LoCoMo categories use the LoCoMo authors’ own mapping, taken from their evaluation code, not the mapping the Mem0 → Memobase → Backboard lineage propagated — which is wrong on three of four. Section 06 has the evidence.

04Reproduce

Fetch the data, run the runner.

One entry point produces every table. The defaults it relies on are --budget 1024 and --model haiku; full_context overrides the budget to 32,000 by design.

shell
./scripts/fetch_data.sh

# LongMemEval, all six categories, oracle haystack, 470 questions
python -m bench.run --dataset longmemeval --variant oracle --all \
    --systems palimpsest,hybrid_rag,vector_rag,bm25,mem0_style,zep_style,full_context \
    --out results/final/lme_oracle_all_categories.json

# Knowledge-update with ~500 distractor sessions per question, 72 questions
python -m bench.run --dataset longmemeval --variant s --all \
    --categories knowledge_update \
    --systems palimpsest,hybrid_rag,vector_rag,bm25,mem0_style,zep_style,full_context \
    --out results/final/lme_s_knowledge_update.json

# LoCoMo, all 10 conversations, 468 questions
python -m bench.run --dataset locomo --all \
    --systems palimpsest,hybrid_rag,vector_rag,bm25,mem0_style,zep_style,full_context \
    --out results/final/locomo_10conv.json

--variant oracle has no distractors and is an upper bound, not a retrieval result. --variant s is the realistic setting. Every run writes per-question records — question, context, answer, judgement, tokens, latency — so any published row can be re-aggregated without re-running anything. Those files are committed under results/final/ and are linked under every benchmark table on the results page.

05The rules

The rules this project binds itself to.

These are constraints on what may be published, not aspirations. They are the reason a page of results carries losses, overlapping intervals and a section about a bug that made the score worse.

  1. One harness, one answering model, one judge, one prompt, every system. Ours and the baselines run in the same process on the same hardware. Any number cited from a paper is labelled as cited and never mixed into a table of things measured here.
  2. Correct category labels, with the mislabelling documented so readers can translate published numbers into the authors’ scheme.
  3. Answer accuracy, generated then judged — never retrieval hit-rate dressed up as accuracy. Where a retrieval ceiling is reported, it is called a ceiling and is never placed beside an answer-accuracy number.
  4. Adversarial included and reported separately, since dropping 446 of 1,986 questions changes what “LoCoMo score” means.
  5. Latency and tokens published, because a memory system that wins on accuracy by stuffing 2,000 tokens into every prompt has not won.
  6. Every number states dataset version, n, answering model, judge model, judge prompt, and micro-vs-macro — in the same place as the number. Almost no published table in this field does, which is the whole reason its numbers cannot be stacked.
  7. If this engine loses a category, that category gets published too. It loses LoCoMo, it loses knowledge-update on the oracle haystack, and both are on the results page at the same weight as the wins.
  8. A confidence interval that overlaps the runner-up is stated wherever the headline appears, not once in an appendix.

Applied to our own headline

In both LongMemEval tables the confidence interval overlaps the runner-up, so the margin over second place is not statistically significant. The margin over BM25 and below is. And we lose LoCoMo.

The same rules were turned on this engine. Four adversarial audits found nine defects, including one where the ledger could see the future and inflate its own results, and one whose fix lowered the LoCoMo score by 9.5 points. Every published number was re-run afterwards and the pre-fix artifacts were withdrawn rather than corrected.

06Comparability

Why other published numbers cannot be placed beside these.

The field’s numbers are not so much wrong as incommensurable. Five things below each move a score by more than an architecture does, and almost no published table states which of them it chose. Verified from primary sources — arXiv full texts, vendor repositories, the dataset files themselves, and issue threads.

Self-reported scores do not survive independent measurement

LightMem is the only system in the field whose self-report reproduces cleanly under third-party measurement. Mem0’s headline is 2.6× its median independent score.

The published LoCoMo category labels are wrong on three of four

From the LoCoMo authors’ own task_eval/evaluation.py, confirmed empirically against the data:

LoCoMo categories as the authors define them, checked against the dataset. Cited, not measured here.
cat n mean evidence items evidence spanning >1 session true label label the Mem0 lineage uses
1 282 3.13 95.4% multi-hop single-hop — wrong
2 321 1.17 8.7% temporal temporal — correct
3 96 2.08 32.3% open-domain multi-hop — wrong
4 841 1.07 0.1% single-hop open-domain — wrong
5 446 1.03 0.0% adversarial —

The Mem0 → Memobase → Backboard lineage uses 1=single_hop, 2=temporal, 3=multi_hop, 4=open_domain. What that lineage reports as “Single-Hop” (282q) is the multi-hop set; what it reports as “Open Domain” (841q) is the single-hop set — the largest and easiest bucket. Supermemory’s memorybench uses a third mapping; Dakera a fourth. No two vendors’ per-category rows are comparable to each other, and none are comparable to the paper.

The dataset in circulation is deprecated

xiaowu0162/longmemeval was marked deprecated and replaced by longmemeval-cleaned on 2025-09-19, which “removes noisy history sessions that interfere with the answer correctness”. Sizes differ — the _s split went from 278,025,796 to 277,383,467 bytes — while the oracle split is byte-identical. Mem0 and Supermemory report on cleaned; Mastra reports on the deprecated original. Those numbers are not comparable and nobody says which was used. This project uses the cleaned release, and says so in every table caption’s accompanying note.

Two confirmed eval-code bugs sit under the published retrieval literature: issue #7, where an empty correct_docs made recall@all equal 1.0 — every retrieval number published before that fix is invalid — and issue #9, still open, where resolve_expansion silently drops items. Known-bad gold answers also survive into the cleaned data.

Free parameters that move a score more than any architecture does

  • Micro vs macro averaging — up to about 6 points on identical data. MemOS is 77.8 micro and 80.45 macro. Mastra’s headline 94.87 is a macro mean; its micro is 93.60. Almost nobody states which. This harness is micro throughout.
  • Denominator. Papers report n = 500, 470, 444, 367, 300, 282, 266, 150, 88, 50, 15 — all called “LongMemEval”. The official tooling itself uses two: run_retrieval.py skips 30 abstention items while print_retrieval_metrics.py averages over 500.
  • Judge choice. Several systems are judged by the same model that answered. The highest verified score in the field, LeanMem’s 91.80, is self-judged. One vendor’s judge prompt adds a paragraph instructing the judge to “be generous” on temporal questions — a category where it then reports 91.90 against a best baseline of 85.05.
  • The long-context baseline spans 14.0 to 82.40 across papers, driven by truncation policy, judge, and model-specific refusal behaviour at 115k tokens — where 63% of one model’s errors are refusals. Any “beats long context by X” claim is unusable without the baseline’s prompt and judge.
  • What is being scored at all. One vendor measures whether the retrieved context contains the gold answer, with no answer-generation step, and places that number beside others’ answer accuracy. Another’s figures are labelled as both “Recall@k=15” and “LLM-as-Judge”.
  • Whose baselines they are. One vendor’s own row reproduces exactly from its committed per-question results, but its seven baseline rows are copied byte-for-byte from another README with no attribution — and those baselines ran on a different, weaker answering model than the row they are printed beneath.

And there is no leaderboard to settle it

There is no public leaderboard for agent memory anywhere. Every vendor publishes its own number, measured its own way, against baselines it chose. That is the situation these measurements were built for, and it is also the reason a single number from this page should not be trusted on its own either — the runner, the raw per-question records and the command that produced them are all published so the number can be checked rather than believed.
